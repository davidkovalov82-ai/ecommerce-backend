# Работа по ecommerce-backend

## Обхват и контекст
- Работи по текущата задача и критериите ѝ за приемане. При поискана реализация завърши договорената функционалност, включително миграции, тестове и необходимата документация.
- ecommerce-learning-plan.md е остарял: не го чети автоматично и не го използвай като действащо изискване.
- Проверявай реализацията в кода и тестовете. Не приемай TODO или резюме за доказателство, че функция работи.
- Преди промени прегледай git status и относимите локални разлики. Запази чуждите и незавършените промени.
- Търси с rg и отваряй нужните файлове, техните зависимости и тестове. Разширявай прегледа при конкретна необходимост; не сканирай целия проект по навик.
- Използвай вече прочетения контекст, докато е наличен и файловете не са променени. След промени преглеждай съответния diff.

## Стек и архитектура
- Приложението е в services/commerce. Следвай pyproject.toml и lock файла: FastAPI, Pydantic, синхронен SQLAlchemy, PostgreSQL, Alembic, pytest, Ruff, uv.
- Запази модулната организация в едно приложение. Отделяй микросервиси само при изрична задача.
- API слоят обработва HTTP и валидацията; service слоят изпълнява бизнес сценария; repository слоят изпълнява заявките към БД.
- Бизнес логиката не зависи от FastAPI. Превеждай бизнес грешките към HTTP отговори на API границата.
- Използвай обща SQLAlchemy Session за един сценарий в заявката, със сигурно затваряне. Не споделяй глобална Session между заявки.
- Service/use-case слоят определя транзакцията и commit/rollback. Repository може да прави flush, но не самостоятелен commit.
- При синхронен достъп до БД следвай съществуващите def обработчици; не блокирай event loop с директни синхронни заявки в async def.
- Използвай класове при нужда от зависимости или състояние. Не превръщай всяка функция в метод. Не добавяй generic repository, Unit of Work или нова зависимост без конкретна полза.
- Парите са цели стойности в най-малката валутна единица, без float. Следвай текущите валутни ограничения.
- Извличай потребителя и правата от проверената автентикация и БД. Проверявай собствеността върху ресурсите.

## Проверки и безопасност
- Промените в схемата получават Alembic миграция. Проверявай ограниченията и съвместимостта със съществуващите данни.
- Добавяй тестове за поведението, значимите грешки и достъпа; повторения и конкурентност — когато сценарият ги изисква.
- По време на работа изпълнявай засегнатите тестове. Преди приключване изпълни пълния suite на commerce и Ruff, ако средата позволява.
- Използвай командите от CI и конфигурацията на проекта, обичайно от services/commerce с uv run --locked.
- Тестовете и техните subprocess команди използват изолирана тестова БД. Не изтривай данни или Docker volumes без изрично разрешение.
- При отказ за изпълнение не повтаряй сляпо и не заобикаляй ограниченията. Посочи блокираната команда; не обявявай непроведени проверки за успешни.
- Не записвай или показвай секрети, токени, пароли и реални лични данни.

## Git и отчет
- Без изрична заявка не изпълнявай git add, commit, push, merge, rebase, reset и не създавай PR. Не променяй клона самостоятелно.
- Преди реализация дай кратко описание на поведението и проверките; не спирай за потвърждение на рутинни решения.
- Накрая посочи какво е променено, действително проведените проверки и оставащите проблеми. Обясни съществените решения кратко на български.
- При приключване обнови docs/session-state.md в корена: до 20 реда с текуща задача, реализирано, непроверено, работещи команди, засегнати файлове и следваща стъпка. Не копирай историята на чата или тези правила.
