## Цель и границы

Сохранить работающий marketplace и разделить владение данными. После K6 существуют шесть самостоятельно запускаемых сервисов: Users, Catalog, Cart, Orders, Payments и Notifications. Это наш этап реализации микросервисной цели проекта roadmap.sh; названия K6.1–K6.4 и порядок выделения являются решениями нашего проекта.

Сохраняем существующее поведение: пользователь покупает и публикует товары от своего имени; администратор управляет пользователями в пределах уже реализованных полномочий; продавец управляет своими товарами и отправлениями. Не вводим обязательный магазин или отдельную регистрацию продавца.

| Владелец | Данные и ответственность |
| --- | --- |
| Users | Учётные записи, хеши паролей, профиль, существующие права и ограничения доступа |
| Catalog | Товары, категории, публикация и модерация товаров, цены, остатки и резервы |
| Cart | Корзина пользователя, её позиции, количество и изменение состава |
| Orders | Заказ, неизменяемые снимки купленных позиций и адреса, статусы, отправления продавцов, координация покупки |
| Payments | Платёжные попытки, Stripe-сессии и webhook, результат оплаты и закрытия платежей |
| Notifications | Приём событий и надёжная доставка уведомлений |

Для пользовательских ID и ID товаров между сервисами сохраняем логические ссылки без внешних ключей в чужую БД. Внутри своей БД ограничения сохраняются. Заказ хранит собственные снимки: изменение или скрытие товара не должно переписывать историю покупки.

HTTP используем для немедленного ответа: чтение, авторизация, создание резерва. RabbitMQ — для фактов, которые должны дойти после сбоя. Outbox хранит исходящее событие в одной транзакции с бизнес-изменением; получатель фиксирует результат и защиту от повторной обработки до подтверждения доставки.

Не добавляем одновременно новые бизнес-функции, Kafka, Redis, Celery, универсальную библиотеку всех сервисов или распределённые транзакции. Kubernetes, автоскейлинг, полноценный API Gateway, Stripe Connect и новые способы оплаты — вне K6. Для сохранения публичных URL допускается простой маршрутизатор; это не отдельный инфраструктурный этап.

## Общий способ выделения сервиса

1. Найти текущие сценарии и тесты; зафиксировать список существующих API и поведение ошибок. Не придумывать новые маршруты вместо проверки кода.
2. Кратко записать владельца данных, HTTP/событийные контракты и поведение при недоступности. Достаточно короткого ADR в docs/: решение, причина, альтернативы и ограничения.
3. Создать сервис с собственными миграциями, зависимостями, конфигурацией и тестами. Перевести вызывающий код на контракт; исключить импорт внутренних модулей и доступ к чужой БД.
4. Подготовить повторяемый перенос существующих данных с сохранением ID. Для учебного развёртывания допустимо окно обслуживания: остановить записи, перенести, сверить данные, переключить владельца. Не вводить незаметную двойную запись.
5. Проверить запуск с пустыми БД и обновление существующих. Для возврата к прежней версии описать ограничения; не обещать откат без потерь после новых записей.
6. Запустить проверки затронутых сервисов и сквозной сценарий. Обновить README, диаграммы, CI и session-state только в части текущего изменения.

## K6.1 — Users

**Результат:** все существующие операции с пользователями выполняет services/users; Commerce обращается к нему через явный контракт.

### Реализация

- [ ] Найти существующие регистрацию, вход, профиль, административные операции, проверки блокировки и зависимости текущего пользователя. Перенести существующий функционал целиком, не добавляя восстановление пароля или OAuth в рамках выделения.
- [x] Создать Users: FastAPI, собственная БД/роль PostgreSQL, Alembic, pytest, Docker и конфигурация Compose. Пароли БД и ключи не записывать в код.
- [ ] Перенести пользователей с сохранением ID и хешей паролей. Проверить количество записей, уникальность, права и состояния; предусмотреть безопасный повтор переноса.
- [ ] Сделать Users единственным владельцем учётных записей. В Commerce убрать ORM-связи и внешние ключи к старой таблице пользователей после переноса нужных сценариев на контракт.
- [ ] Сохранить публичные URL либо задокументировать совместимую маршрутизацию. Старый и новый сервис не должны параллельно изменять пользователей.
- [ ] Определить авторизацию до написания интеграции. Рекомендуемая цель — подписанные access-токены с асимметричной подписью: закрытый ключ только в Users; проверка подписи, срока, issuer и audience в потребителях. Изменение токенов требует явной стратегии для уже выданных токенов.
- [ ] Сохранить действующие гарантии блокировки и изменения прав. Для первого выделения можно проверять актуальное состояние пользователя через внутренний HTTP Users при защищённой операции; локальная подпись токена сама этого не гарантирует. Указать зависимость от доступности Users, ограничить таймауты и запрещать защищённую операцию, если статус проверить невозможно. Оптимизацию через кэш/события отложить до измеримой необходимости.
- [ ] Не доверять клиентским role, seller_id и user_id. Межсервисный доступ аутентифицировать; внутренние маршруты не открывать публично.

### Критерии приёмки

- [ ] Старый пользователь входит после переноса; новый регистрируется, входит и использует существующий профиль.
- [ ] Владелец может изменить свой товар; посторонний получает отказ. Блокировка и изменение прав действуют согласно зафиксированному контракту даже при старом access-токене.
- [ ] При недоступном Users защищённая операция не получает доступ по умолчанию. Публичное чтение каталога не требует запроса к Users, если раньше оно было публичным.
- [ ] Ни один потребитель не читает таблицы Users напрямую. Отдельный запуск, миграции, CI и сквозная покупка работают.

**Первое действие ИИ:** кратко назвать найденные пользовательские API, затрагиваемые таблицы и выбранный способ проверки блокировки. Затем реализовать весь K6.1, не переходя к Catalog.

## K6.2 — Catalog и резервы

**Зависимость:** K6.1 готов. **Результат:** Catalog единолично управляет товарами и остатками; Orders больше не меняет их SQL-запросами.

### Реализация

- [ ] Сначала определить и проверить контракт резерва в существующем приложении, затем перенести его за HTTP без изменения бизнес-правил.
- [ ] Выделить товары, категории, существующий поиск/фильтрацию, владение и модерацию в services/catalog с собственной БД, миграциями и переносом данных.
- [ ] Создание резерва выполняет Catalog по текущим ценам и доступности. Зафиксировать момент окончательной фиксации цены заказа. Нельзя доверять цене, присланной покупателем.
- [ ] Определить ID резерва, заказ, позиции, срок и состояния; команды создания, подтверждения списания и освобождения. Повторы с одним ключом возвращают прежний результат; несовместимые параметры с тем же ключом отклоняются.
- [ ] При таймауте Orders сохраняет неизвестный исход и выясняет результат по устойчивому идентификатору, не создавая второй резерв. Поздний ответ, отмена и повторное выполнение обрабатываются согласованно.
- [ ] Определить владельца истечения резерва. Catalog не должен автоматически возвращать товар в продажу, пока оплата может завершиться: согласовать закрытие Stripe с Payments/Orders и сохранить защиту от поздней оплаты.
- [ ] Перенести чтение товаров и изменение остатков из Commerce/Cart на контракт Catalog. Сохранить снимки заказа и существующие ограничения продавцов.

### Критерии приёмки

- [ ] При одновременной покупке последней единицы резерв получает только один покупатель; доступный остаток не отрицательный.
- [ ] Повторы создания, подтверждения и освобождения не меняют остаток второй раз. Проверены потерянный ответ и рестарт между шагами.
- [ ] Отмена и истечение освобождают резерв один раз; оплаченный или ещё неопределённый платёж не приводит к преждевременной продаже товара другому покупателю.
- [ ] Сбой Catalog не создаёт частично оформленный заказ без предусмотренного восстановления. Прямого доступа Orders к его БД нет.
- [ ] Проходят прежние сценарии оплаты, отложенной оплаты, отмены и уведомлений.

## K6.3 — Cart

**Зависимость:** K6.2 готов. **Результат:** services/cart владеет корзинами; текущие GET /cart, PUT /cart/items/{product_id}, DELETE /cart/items/{product_id} сохраняют поведение.

### Реализация

- [ ] Выделить хранение корзины, миграции, API и проверки собственности; перенести существующие корзины с сохранением связей по ID.
- [ ] Получать необходимые сведения о товарах через Catalog. Корзина не владеет остатками и не резервирует товар только из-за добавления позиции.
- [ ] Дать Orders контракт получения состава корзины. Оформление повторно проверяет цены и наличие через Catalog; цена корзины не является обещанием цены покупки.
- [ ] Защитить повторное оформление от второго заказа и резерва. Определить версию/снимок корзины и очистку купленных позиций: параллельные изменения пользователя нельзя случайно удалить.
- [ ] При недоступности Cart/Catalog возвращать предусмотренную ошибку; не создавать заказ с непроверенными позициями.

### Критерии приёмки

- [ ] Чужая корзина недоступна; добавление, замена количества, удаление и просмотр работают после переноса.
- [ ] Проверены изменение цены, скрытие товара и нехватка остатка между наполнением корзины и оформлением.
- [ ] Повтор оформления не создаёт второй заказ; изменение корзины во время оформления не теряется. Запросов к чужим таблицам нет.

## K6.4 — Orders и общая сборка

**Зависимость:** K6.1–K6.3 готовы. **Результат:** остаток Commerce становится services/orders; перенос не создаёт седьмой сервис-дубликат.

- [ ] Оставить в Orders заказы, снимки цен и адресов, отправления продавцов и координацию резервов, оплаты и отмены. Сохранить независимые отправления продавцов при общей оплате заказа.
- [ ] Обновить имена сервиса, запуск, миграции, ссылки в Compose, CI и документации. Переименование не должно создать пустую БД вместо существующих заказов или потерять миграционную историю.
- [ ] Проверить права БД: учётная запись каждого сервиса не имеет доступа к чужим таблицам. Сервисы не импортируют соседние app-пакеты.
- [ ] Проверить готовность сервисов, ограниченные сетевые таймауты и полезные логи с order_id, reservation_id, payment_attempt_id/event_id там, где они существуют. Не логировать секреты и содержимое персональных данных.
- [ ] Для изменённых событий определить порядок развёртывания: сначала готовый получатель, затем отправитель. Не выкатывать новый контракт на несовместимый потребитель.
- [ ] Обновить диаграмму сервисов, владение таблицами, команды запуска и пошаговую демонстрацию.

### Итоговая приёмка K6

- [ ] Шесть сервисов запускаются в Docker Compose документированной командой; каждый имеет собственные миграции и набор проверок CI.
- [ ] Выполняется покупка: вход → товар → корзина → заказ/резерв → Stripe → оплаченный заказ → уведомление и дальнейшая отправка продавцом.
- [ ] Проходят тесты последней единицы, повторов оформления, отмены без первой оплаты, отложенной оплаты, потерянного ответа и восстановления прерванной отмены.
- [ ] Остановка Payments, Notifications, RabbitMQ или одного из новых сервисов не теряет уже сохранённый результат; после восстановления система сходится к предусмотренному состоянию. Для каждого теста указаны ожидаемые ошибки и восстановление.
- [ ] Проверены новые БД и перенос прежних данных; K4/K5 регрессии адаптированы и проходят. Прогоны через локальный Stripe mock и настоящий Sandbox явно различаются в отчёте.
- [ ] Масштабируемость не объявляется доказанной количеством сервисов. Нагрузочные измерения и Kubernetes остаются отдельными этапами.

## Как завершать каждый блок

Код проверен, миграции и перенос работают, необходимые тесты действительно запущены, ограничения названы. Обновлены затронутые инструкции и docs/session-state.md. Пользователю переданы краткое объяснение изменений и результаты проверок. Следующий блок, Git-операции и развёртывание без отдельной просьбы не начинать.
