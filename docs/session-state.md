- **Текуща задача**: Етап К5 (`feat/payments-service`) — поправка на 3 конкурентни/reconcile сценария в Payments (без `commit`/`push`/`merge` и без преход към К6).
- **Реализирано**:
  - Сценарий 1 ([`PaymentService`](file:///Users/kovalovdavid/Projects/ecommerce-backend/services/payments/app/service.py)): `reconcile_single_attempt` и `_sync_after_expire_conflict` пазят терминалните статуси (`failed`/`succeeded`/`expired`/`declined`) и не емитират `payment.processing` при остарял Stripe отговор `complete`/`unpaid`, без да държат DB lock по време на Stripe заявките.
  - Сценарий 2: в безопасното окно `stripe_idempotency_window_seconds` (24ч) сверката повтаря заявката със същия `idempotency_key`/параметри (`_recover_initiated_session_in_window`) и затваря възстановената отворена сесия при Stripe преди `payment.expired`; извън окното записва `PaymentDiscrepancy(source="reconcile", reason="idempotency_window_expired")` без нова сесия; в Commerce `stock` се връща веднъж.
  - Сценарий 3: [`0003_expand_order_closures_status`](file:///Users/kovalovdavid/Projects/ecommerce-backend/services/payments/migrations/versions/0003_expand_order_closures_status.py) разширява `payment_order_closures` с временни `cancelling`/`expiring`, блокиращи нов `checkout` с `409` до финализиране или rollback на отмяната.
