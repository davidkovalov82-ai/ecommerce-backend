## К1. Публикация товаров от имени пользователя

**Приоритет:** P0 — следующий этап разработки.

**Цель:** любой зарегистрированный пользователь может покупать товары и публиковать собственные объявления с одного аккаунта. Открывать магазин, подавать заявку или получать отдельную роль `seller` не требуется.

### Правила владения

- У каждого товара один владелец — пользователь, который его опубликовал.
- При создании товара сервер устанавливает `seller_id` по текущему авторизованному пользователю. Клиент не выбирает владельца и не может передать товар другому пользователю через редактирование.
- Владелец может редактировать и деактивировать свои товары. Право администратора на модерацию — отдельное полномочие: оно не даёт права менять цену или остаток чужого товара через API продавца.
- Публикация товара не меняет права покупателя: пользователь по-прежнему может пользоваться корзиной и оформлять заказы.

### Поведение API

| Запрос | Ожидаемое поведение |
| --- | --- |
| `POST /products` | Авторизованный пользователь публикует товар от своего имени и получает `201`. |
| `PATCH /products/{id}` | Владелец редактирует свой товар, в том числе неактивный. Для чужого и несуществующего товара ответ одинаковый — `404`. |
| `GET /users/me/products` | Возвращает только товары текущего пользователя, включая неактивные. Пагинация — по тем же правилам, что и в публичном каталоге. |
| `GET /products` и `GET /products/{id}` | Сохраняют существующий публичный контракт: видны только активные товары. |

Без авторизации создание, редактирование и просмотр личного списка возвращают `401`. Если клиент явно передал `seller_id` в теле `POST` или `PATCH`, сервер возвращает `422`. Существующие проверки цены, валюты, остатка и остальных полей сохраняются.

### Данные и миграция

Добавить обязательное поле `products.seller_id` со ссылкой на `users.id`. Для существующих товаров, чей автор неизвестен, использовать техническую учётную запись без возможности входа. Не назначать такие товары первому пользователю или администратору.

Порядок миграции: добавить поле как допускающее `NULL` → заполнить владельца у существующих товаров → установить `NOT NULL`. Миграция должна сохранить ID товаров, цены, остатки и существующие ссылки на товары.

### Когда К1 готов

1. Анна и Борис регистрируются как обычные пользователи. Каждый публикует товар без дополнительных действий. Оба активных товара видны в публичном каталоге.
2. Борис пытается изменить цену товара Анны по известному ID. Получает `404`, цена остаётся прежней. Анна отправляет такой же запрос со своей авторизацией — цена меняется.
3. Анна деактивирует товар. Он исчезает из публичного каталога, остаётся в её личном списке и не появляется в личном списке Бориса.
4. Попытки указать чужой `seller_id` при создании и сменить владельца через `PATCH` отклоняются. Владение не меняется.
5. Миграция проверена на базе, в которой до обновления уже был товар. После обновления у него есть владелец, а его ID, цена и остаток сохранены.
6. Проверки поведения добавлены в тесты. Полный набор тестов `commerce` и Ruff проходят.

**Граница этапа:** К1 отвечает за публикацию и владение товарами. Компании и их сотрудники, блокировка пользователей, модерация объявлений, обработка заказов продавцом и выплаты продавцам — отдельные задачи. Для завершения К1 реализовывать их не нужно.
